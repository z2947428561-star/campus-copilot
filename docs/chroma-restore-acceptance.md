# 问题 4：Chroma 换目录恢复验收

日期：2026-10-18。基线：`90f23b8`。分支：`codex/portable-chroma-releases`。
本次处理 Chroma 绝对路径参与登记身份，导致换目录后发布记录不可见的问题。

## 修复结果

新登记使用向量目录相对于登记库所在目录的位置。
关闭使用 Chroma 的进程后，同时复制登记库和完整向量目录，保持相对布局，
将配置指向新位置，即可保留活动版本、上一版本、历史候选和修订号。
独立存储目录及逻辑集合名仍隔离；Milvus 的登记身份不变。
Windows 跨盘无法表示相对位置时仍使用绝对身份，可显式重绑定。

原位置的旧登记只读兼容，查询不改库；下一次构建、发布或回滚时，事务内转换为新登记格式。
旧备份已换目录时，新增命令完成迁移：

```powershell
# 当前配置指向恢复位置；下面的旧路径和修订号需要替换。
.venv\python.exe scripts/build_kb.py --rebind-from 'E:\old-project\data\chroma_db' --expected-revision 2
.venv\python.exe scripts/build_kb.py --status
```

重绑定前校验源修订号、活动模型配置，以及所有 `ready` 集合的度量、分块数量、分块 ID、正文和元数据哈希。
校验成功后，在同一 SQLite 事务中迁移指针和全部构建记录，不合并目标已有记录。
重绑定保留备份修订号，后续发布和回滚继续递增；操作不调用模型或 Embedding 服务。
校验失败或数据库写入失败时登记不变。哈希校验范围不包含向量字节或检索语义质量。

完整操作及找回旧修订号的方法见[存储说明](storage.md)。本轮只使用临时测试数据，未迁移现用索引。
正在运行的后端需要重启后加载新实现。

## 可重复验证

在项目根目录运行，不需要账号、模型密钥、Milvus 或个人数据库：

```powershell
.venv\python.exe scripts/test_kb_restore.py
.venv\python.exe scripts/test_chroma_rebuild.py
```

恢复脚本使用真实临时 Chroma、确定性向量和独立子进程。
每次待发布进程退出后才复制文件，恢复进程重新加载登记与集合。
最小案例在修复前失败：恢复后活动版本变成 `legacy`；修复后保留原版本且能查询原文。

专项范围包括：

1. 整套目录迁移后保留发布记录并实际检索。
2. 新格式、旧绝对路径格式和跨盘绝对格式的恢复、浏览器读取、回滚、暂存版本再发布；跨盘格式模拟无法计算相对路径的情况。
3. 205 分块候选和未完成构建的记录保留，旧修订号发布仍被拒绝。
4. 旧格式查询不写库，正常写入后转为可迁移格式，再次换目录仍可读。
5. 集合缺失、后续批次的正文或元数据变化、修订号过期、目标已有记录、模型不符、源路径错误均拒绝重绑定。
6. 迁移第二张表时注入 SQL 错误，验证活动指针和版本记录一起回滚。
7. 两个重绑定并发时只有一个成功；不同存储仍隔离，只复制登记库不会复用旧读取缓存。

七项恢复专项及十五项既有发布专项已通过。
完整离线回归通过 19 个检查文件，包含用户原有爬虫测试；相关 Python 文件编译和差异空白检查通过。
本轮完成后停止，交由用户验收。
